**B-01.** The LOOKUP step's key and manifest say which index the step depended on, but they are computed from one hash. The lookup observations, and through them the evidence ids, claim ids and C(J), come from a second hash taken later by the adapter. Nothing compares the two. If the index file changes between them and is put back before the next step, the investigation completes, verifies and replays as "reproduced" on lookups from a different index. MM P6 relies on "LOOKUP is a function of … the pinned index", and this breaks it. If the file is not put back, the next step's staleness check catches the change (STALE), so the gap needs a change-and-restore during LOOKUP.

**B-02.** The docstring in `lookup.py` says an unavailable index is "an identity value too", while MM 10.2 says it is a failure, not stale. The practical effect: a moved, unmounted or permission-broken index at any resume after LOOKUP turns a long investigation into a terminal STALE, which no repair can undo.

**B-03.** Step 8 verified the side channel against a child kill and a controller kill, but not against loss of the work directory. The Stage 03 gate does not cover the gap, because it records the instant only after reading the body. Because the file lives in `/tmp` and its directory entries are never fsynced, a power loss is exactly the case where the safeguard can disappear.

**B-04.** This was reproduced with the repository's own synthetic child. Safety holds: no early request is sent. The defects are the misleading `retryable=true` record and a terminal code that names an adapter defect. Treat it as a correctness-of-classification issue for the owner.

**B-05.** This contradicts the D-044 ordering that `open_controller` documents ("a workflow-corrupt journal is never repaired"). The two entry points (`run` and `resume`) behave differently on the same journal.

**B-06.** An operator told "not found" may conclude the investigation does not exist. No data is lost: a later `run` is refused with exit 3.

**B-07.** `show` and `verify` (with `MEMORY_OPEN` and `WORKFLOW_INVARIANTS` reported PASS) treat as valid a journal that `resume` declares CORRUPT. The CORRUPT/verify-failed/incomplete distinction should not depend on which command was run.

**B-08.** It only matters for a forged journal (D-046 notes there is no tamper protection) or a defective ASSEMBLE. Memory's check on open is still weaker than the D-054 statement it is meant to enforce.

**B-09.** It is latent today, but it misreports the D-054 graph as orphan blobs. Any future cleanup or export built on `orphan_blobs()` would silently drop report chunks.

**B-10.** The code reaps before scanning only on the normal-exit path, the opposite of its own timeout path. This is a low-probability reliability gap, inferred from code reading and not reproduced.

**B-11.** A documentation mismatch; the behaviour is deliberate and tested.

**B-12.** Performance only; it overlaps A11-4. It is listed so the step 12 optimisation has the full set of multipliers.

**B-13.** A resource-bound statement is missing; this is an inference with no measurement.

## 3. Notes for D-062 (index identity change)

1. **Compute the identity once and bind both uses (B-01).** Today the index identity is computed independently in `plan.Integration.environment` → `environment_identity` (step keys, manifests, staleness) and in the LOOKUP adapter's `index_identity(index, sha)` (written into every lookup observation and so into evidence, claim ids and C(J)). Compute the verified canonical identity once per LOOKUP attempt, and make the controller assert the keyed identity equals the observed one.
2. **Keep the integrity guard out of the scientific identity.** `identity_digests` (`workflow.py:573-582`) digests the whole dict the environment returns. If the raw file hash or stat tuple stays in that dict, a byte-different rebuild still turns the investigation STALE through S-10.1. The guard must sit outside `IDENTITY_NAMES` and outside the lookup observation blob (`lookup.observe` embeds `index` in every observation).
3. **Reuse and fingerprint.** `current_digests()` is called before every step and in `check_stale` (10 hashes per run, measured). D-062 allows per-process reuse keyed by a strong fingerprint. The identity source is called as a stateless function today, so the cache has to live in `Integration` (per process). The fingerprint should include `st_ino`, `st_dev`, `st_size`, `st_mtime_ns` and `st_ctime_ns`; mtime alone can be restored. Do not weaken the LOOKUP before/after guard: copy-in-place and restore can defeat stat-only comparisons, so keep the hash or the content verification there.
4. **Failure mapping (B-02).** Verification failure ("stored digest forged") must not become another identity value that silently marks the investigation STALE where MM says failure, and must not surface as `IDENTITY_UNAVAILABLE`, which reaches the CLI as exit 1 (internal). Decide and specify which of FAILED (LOOKUP not yet run), failure without STALE, or STALE applies at each phase.
5. **Two staleness implementations.** `controller.stale_payload` and `operations.stale_identities` are near-duplicates (B-07). An identity change has to be made in both, or they must be unified first.
6. **Same view of the file.** Stage 02 opens the index `mode=ro&immutable=1` (`store.py:564`), so a `-wal` sidecar is ignored. The canonical verification should read the database the same way the queries do, so both see the same content.
7. **Version bumps.** Removing `index_sha256` from the lookup observation changes the observation schema. The `INTEGRATION_SCHEMAS["lookup-observation"]` version and the Stage 04 identity (I-3/A-6) must move together. Every development journal then becomes STALE, which D-062 accepts.
8. **VERIFY.** `STAGE02_INDEX_IDENTITY` (`verify.py:234-248`) should also compare the recorded canonical identity with the LOOKUP manifest's `identities.index` (B-01), and re-verify it against the current index only in the read-only `verify` and `replay` commands.

## 4. Checked, no finding

- **Journal format 4 and the torn tail.** `parse_journal` and `_tail_problem` (`journal.py:77-148`) match SPEC 8.6, D-044 and D-046. The complete torn record is validated with `Folder.check` before repair (`memory.py:266-275`). Copy → Verify → Preserve, with read-back checks and a re-read equality check, is implemented; a read-only open writes nothing. The append truncates back and fsyncs on any failure (`journal.py:170-192`).
- **Blobs.** Create a temporary file with `O_EXCL`, write, fsync, read back and hash, publish with `link`, fsync the directory. An existing name is re-verified and fsynced again (`blobs.py:519-566`). Temporaries are removed only by a writable open after validation.
- **Lock.** Exclusive non-blocking `flock`; the inode is rechecked after locking and before every append (`lock.py:401-448`). BUSY is exit 13. Read-only opens also take the exclusive lock, so concurrent `show` calls return BUSY, consistent with SPEC 10.1.
- **Fold.** M-1, M-2, M-6, M-9 and M-14, attempt numbering and the content-commits-only-on-`step_succeeded` rule (`fold.py:594-680`). D-053 and D-055 series, order and boundaries are rechecked at `step_succeeded` (`:413-452`). `batches.boundaries` is correct for compact canonical encoding.

- **Retry and deferral.** A_MAX, F_MAX and φ follow SPEC 9.2. `recover()` writes `step_interrupted`, or `RETRY_BUDGET_EXHAUSTED` when the budget is spent, before anything else. `not_before` is enforced in `_guard_start`. `MAX_ACTIONS = 32` is at least the reachable maximum (7×3 + 9 + 2).

- **D-042 bound.** The timer starts before `Popen`; the child is frozen, its process tree read from `/proc`, SIGKILLed per process and per group before the leader is reaped, then swept for 5 s; survivors fail closed; `PR_SET_PDEATHSIG` is set and the parent pid rechecked. - **Exit codes.** Corrupt 12, stale 11 and failed 9 are mapped as documented, apart from B-06 and B-07.
- **D-048 bound.** Enforced per query through `gather_bounded`, all or nothing (`investigation/lookup.py`).
- **Journal size.** The 512 MiB journal and 1 MiB record ceilings are enforced on append and read (`memory.py:338-344`). The D-055 proof (maximal journal ≤ 8.64 MB) was not rechecked; I relied on `bounds.json` as cited.
