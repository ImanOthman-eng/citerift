## 1. Claim under test

On fresh, randomly drawn arwiki and enwiki articles that cite at least one work
by DOI, and inside a seeded window of each article, the extractor finds the
reference definitions, citation units, uses and DOI/PMID occurrences that a
separate inspector finds in the raw source; binds uses to definitions; gives
identifiers their correct normalized key and markup role without promoting
notice, marker or title identifiers to cited-work identifiers; links source uses
to the rendered footnote markers without wrong attachments; and never reports
"no warning" where the rendered reference shows one. The claim is about **this
sample**; section 7.3 states what it does not support.

and tested in that language; "partial" means extracted and reported with the stated
limitation; "unsupported" means reported as an exception, never dropped.

## 3. Splits

| Split | Selection | Use |
|---|---|---|
| development | purposive (`../calibration/dev_selection*.json`), 12 revisions | calibration only |
| holdout | `select_sample.py`, positions 1-10 per wiki | gates |
| reserve | positions 11-16 per wiki | added in order, before any prediction, only while the locked annotations fall short of the minimum denominators (7.2) |
| confirmation | positions 17-22 per wiki | only after a material repair that follows exposure of holdout predictions (section 9) |
| challenge, observed | `select_sample.py`, up to 3 per wiki transcluding a retraction-marker template | reported separately; G7 also applies |
| challenge, synthetic | committed test fixtures under `tests/stage03/`, labelled SYNTHETIC | exact expected outcomes (section 10) |

Population for the holdout: articles in namespace 0, not redirects, whose current
rendered output has at least one `https` external link to `doi.org` (MediaWiki
`prop=extlinks`, `elquery=doi.org`) at selection time. `list=random` gives the
random draw (500 per batch, at most 4 batches per wiki); its answers are kept so
the draw can be audited, though not re-run. Development articles are excluded by
title; all revisions of an article belong to one split. Eligible articles are
ordered by SHA-256 of `citerift-stage03-holdout-v1|<wiki>|<page id>`. The latest
revision at capture time is pinned by `citerift-wiki capture --page-id`. An
article whose capture fails stays in the split and counts in acquisition success;
the next reserve article is **not** substituted for it.

Leakage check: the scorer reports annotated holdout keys that also occur in the
development extractions (shared cited works are possible and are reported, not
removed).

## 4. Annotation

1. A separate evaluator agent with its own context labels each article from the
   raw `source.wikitext` and `render.html` under `ANNOTATION_GUIDE.md`. It does not
   see extractor code or output. Several instances may be used (for example one per
   language); each records its provenance. This is procedural independence between
   AI agents, not human gold and not owner review.
2. The executor builds the packets (`evaluate.py packets`) from the capture bundles;
   packets hold only raw artifacts and the window.
3. When the evaluator finishes, `evaluate.py lock` writes `ANNOTATION_LOCK.json` and
   the executor commits the annotations and the lock. **No holdout or challenge
   extraction is run before that commit.**
4. Window: 8000 code points starting at the line that holds a seeded-random `<ref`
   opening (function `window` in `evaluate.py`), or the whole article when shorter.
5. Disagreements after scoring are listed per item. The evaluator (a new instance,
   given the guide, the raw artifacts, its locked label and the extractor's value
   for the disputed items only) may confirm or correct each label and must give a
   reason. Corrected files are stored as `adjudicated/`; the scorer reports both
   label sets, and the item-level differences are published. Gates use the
   adjudicated labels; the locked results are always shown next to them. The
   executor never edits a label.

## 5. Units and matching (implemented in `evaluate.py`)

| Unit | Annotated position | Predicted item | Match |
|---|---|---|---|
| definition | start of the definition | each definition of each container (or the container span for bibliography entries) | the annotated start lies in the predicted span; nearest start wins; one to one |
| unit (template) | start of the citation template | `citation_template` / `external_data_template` units | as definitions |
| unit (unstructured) | flag on the definition | `unstructured_text` unit | inside the engine definition matched to that definition |
| use | start of the use | uses | as definitions |
| binding | `binds_to` location or `missing` | the use's container | correct when the location lies in any definition of that container, or both say missing |
| identifier | raw-text span and scheme | identifier occurrences (excluded occurrences are not predictions) | same scheme and overlapping spans; largest overlap; one to one |
| render link | `render_ref_id` | the use's matched footnote marker id | equal ids |
| marker | label per matched definition | the container's marker state | mapping in section 6 |

Scope: annotated and predicted items are counted when their own start lies in the
window. Annotated items whose quote does not occur at the stated position are
reported as invalid and left out.

## 6. Metrics (per language; micro over items; per article in the raw rows)

- definitions, units, uses, identifiers: TP, FP, FN, precision, recall; an
  identifier the evaluator labelled `not_a_target` that the engine reports as an
  identifier is a false positive;
- container grouping: agreement on whether two matched definitions belong to the
  same named reference;
- binding accuracy = correct bindings / matched uses with a definite annotated binding;
- normalized-key error rate = matched target identifiers with a different key /
  matched target identifiers;
- promotions = matched identifiers labelled `marker_target`, `textual_mention`
  or `not_a_target` that the engine gives `primary_citation_field` or
  `identifier_link`; role agreement over matched target identifiers;
- render linking: precision = correct / engine links; coverage = correct /
  linkable (annotated uses with a marker id); false attachments = engine links to a
  different marker, or to a marker where the evaluator found none; abstentions;
- markers: confusion matrix of evaluator label × engine state (engine
  `recognized_warning_text`→warning, `ambiguous_text`→ambiguous,
  `missing_template_link_only`, `no_recognized_warning_in_inspected_region`→none,
  `not_inspected`/`unavailable`→not_inspected); fabricated negatives = evaluator
  `warning` × engine `none`; `not_inspected` counts;
- exact anchors: every source anchor and DOM locator re-verified by
  `citerift-wiki verify` on every evaluated bundle;
- acquisition: per selected article, capture state (`complete`, `partial`,
  `deferred`, `failed`) with its issue codes; replay: `citerift-wiki replay` on
  every evaluated extraction;
- uncertainty: 95 % article-cluster bootstrap intervals (2000 resamples, seed
  20261028) for the main ratios; zero denominators reported as N/A.

## 7. Gates

### 7.1 Values (each language separately, adjudicated holdout labels)

| Gate | Requirement |
|---|---|
| G1a / G1b | identifier precision ≥ 0.97; recall ≥ 0.90 |
| G2 | normalized-key error rate ≤ 0.01 |
| G3a / G3b | promotions = 0; role agreement ≥ 0.90 |
| G4a / G4b / G4c | use precision ≥ 0.97; recall ≥ 0.95; binding accuracy ≥ 0.97 |
| G5a-d | definition precision and recall ≥ 0.95; unit precision and recall ≥ 0.95 |
| G6a / G6b / G6c | render link precision ≥ 0.98; false attachments ≤ max(1, 1 % of engine links); coverage ≥ 0.85 |
| G7 | fabricated negative markers = 0 (holdout and observed challenge) |
| G8 | every evaluated bundle and extraction verifies (`verify` exit 0); every exact anchor and receipt hash checks |
| G9 | every selected article ends with a recorded capture state; at least 80 % of selected holdout articles per wiki captured with source and render; failures listed with codes |
| G10 | replay reproduces every evaluated extraction digest (100 %) |
| G11 | every synthetic challenge case meets its exact expected outcome (section 10) |

### 7.2 Minimum denominators and sample size

Per language, before predictions: at least 50 annotated target identifier
occurrences, 80 uses, 60 definitions and 60 linkable uses. The development
windows held 6-21 definitions, 7-22 uses and 0-23 identifier occurrences each
(`evidence/selftest_dev.txt`); random DOI-citing articles are
expected to be smaller, so the holdout starts with 10 articles per wiki and adds
reserve articles in order, two at a time, up to 16, only on the counts of the
locked annotations. If 16 articles do not reach a minimum, the affected gate is
reported against the actual denominator and the claim is narrowed accordingly;
it is not reported as met.

Why these sizes: the review effort of one evaluator over about 20-32 windows of
8000 code points is bounded (about 300 k code points of wikitext plus HTML), and
the observed per-window counts make 50-150 items per language attainable. With
those counts the gates are **sample checks**, not population guarantees: with
zero errors in 50 items the one-sided 95 % Clopper-Pearson upper bound on the
error rate is 5.8 % (3.0 % at 100, 2.0 % at 150); with one error in 50 it is
9.1 %. Items within an article are correlated, so the bootstrap intervals over
articles are reported next to every ratio.

### 7.3 Why these thresholds

- **Task risk.** Stage 04 will look identifiers up in retraction data. A wrong
  key, a notice or marker DOI promoted to the cited work, or a use attached to the
  wrong rendered footnote would produce a false "cites a retracted work" or a
  misplaced warning. These are guarded hardest: promotions and fabricated
  negatives must be zero, key errors at most 1 %, render precision at least 0.98
  with at most one wrong attachment in a small sample. A missed identifier yields
  no finding (absence is never reported as "not retracted"), so recall
  requirements are lower but still prevent an "abstain on everything" pass:
  identifier recall 0.90, render coverage 0.85, use and definition recall 0.95.
- **Baseline.** On the development windows the simple structural baseline B1
  differs from the engine in exactly the guarded places: its order-based render
  linking attaches all or all but one of the uses to a different marker in 5 of
  12 windows (7-22 uses each), it misses 19 of 21 definitions (all bibliography
  entries) in one Arabic window, and it reports 2 marker DOIs as citations in one
  English window (`evidence/selftest_dev.txt`). A
  gate that B1 could pass on those properties would not test the design.
- **Annotation uncertainty.** One AI evaluator will make some mistakes; precision
  gates below 1.0 (other than the zero-tolerance ones) and the recorded
  adjudication absorb isolated label errors without hiding them.
- **Not lenient by construction.** No threshold was chosen from holdout results
  (none exist at the freeze), and none is set at the engine's development
  agreement with its own output (which is 1.0 by definition and says nothing).

## 8. Baselines and the A/B/C comparison

- **B0** (Stage 01, valid task only): for each DOI key the evaluator recorded in
  scope, is the key present in the wikitext (case-insensitive, or URL-encoded)?
  Reported: keys, found, and found keys that the evaluator never labelled as a
  cited-work identifier. No extraction recall is attributed to B0.
- **B1** (simple structural): regular expressions over `<ref>` tags; names bind
  to the first definition with that name (groups ignored); identifiers from
  `doi=`/`pmid=` fields and resolver URLs inside ref bodies; the k-th use linked to
  the k-th rendered footnote marker; a warning when a fixed word occurs in the ref
  body. Scored with the same matcher and metrics as the engine.
- **A/B/C**: for each annotated cited-work DOI occurrence, relocate the evidence
  from (A) the DOI and the revision URL only, (B) the exact source anchor only,
  (C) the full ledger (anchor, container, rendered note, uses, markers). Reported:
  unique and correct source relocation, rendered-note relocation (correct, wrong,
  ambiguous, abstained), uses relocated, wrong targets, and record bytes. Extraction
  time and memory for C come from the holdout extractions; A and B need none beyond
  a text search. Review effort is not measured (no independent way to measure it).

## 9. After predictions

Predictions are produced once, with the frozen code at a recorded commit. A failed
gate is reported as failed, with its rows. If a material defect is repaired after
exposure, the repaired engine is evaluated once on the confirmation articles
(positions 17-22), annotated and locked the same way before its predictions; the
old holdout result stays published and is not called fresh. At most one repair
round is run; anything further goes to the owner.
